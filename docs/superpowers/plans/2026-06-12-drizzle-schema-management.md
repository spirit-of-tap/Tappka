# Drizzle Schema Management Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make Drizzle ORM the schema source of truth and migration generator for this Supabase project, with zero runtime changes and zero production risk.

**Architecture:** `drizzle-kit pull` introspects the *local* database into TypeScript schema files (split per domain under `db/schema/`). Future migrations are generated by diffing those files (`drizzle-kit generate`) into `supabase/migrations/` with Supabase-style timestamps, applied by the Supabase CLI exactly as today. Triggers and functions, which Drizzle cannot model, live as current-state SQL in `db/sql/`. App data access stays 100% on `supabase-js`.

**Tech Stack:** drizzle-orm + drizzle-kit (dev-only), Supabase CLI 2.72.9, local Postgres at `postgresql://postgres:postgres@127.0.0.1:54322/postgres`.

**Spec:** `docs/superpowers/specs/2026-06-12-drizzle-schema-management-design.md`

---

## Hard rules for the implementer

1. **Never run anything against production.** Every command in this plan targets the local Supabase stack only. Do not run `supabase db push`, `supabase migration repair`, or `supabase link` against any remote.
2. **Do not modify or delete any of the 30 existing files in `supabase/migrations/*.sql`.**
3. Local stack must be running (`pnpm supabase:start`) before introspection tasks.

```bash

```

- [ ] **Step 2: Create `drizzle.config.ts` in the repo root**

```typescript
import { defineConfig } from "drizzle-kit";

// Schema-management only: drizzle-kit diffs db/schema/*.ts against the
// snapshot in supabase/migrations/meta and writes timestamped migration
// files that the Supabase CLI applies. The app never connects via Drizzle.
export default defineConfig({
  dialect: "postgresql",
  schema: "./db/schema",
  out: "./supabase/migrations",
  schemaFilter: ["public"],
  migrations: {
    prefix: "supabase",
  },
  entities: {
    roles: {
      provider: "supabase",
    },
  },
  dbCredentials: {
    // Local Supabase stack only — never point this at production.
    url: "postgresql://postgres:postgres@127.0.0.1:54322/postgres",
  },
  verbose: true,
  strict: true,
});
```

```bash

```

Expected: prints a drizzle-kit version (1.x or 0.31+), no errors.

Create `db/schema/` and distribute the generated table/enum definitions according to the domain split table at the top of this plan. Rules:

- Delete `relations.ts` content — we do not use Drizzle's relational query API (YAGNI; no runtime Drizzle).

- [ ] **Step 3: Fix the auth.users foreign key**

In `db/schema/profiles.ts`, the `users` table has `users_auth_user_id_fkey → auth.users.id`. The introspected output may reference a placeholder table named `usersInAuth` (defined at the top of the generated schema.ts via `pgSchema("auth").table("users", ...)`). Replace that placeholder with the official helper:

```typescript
import { authUsers } from "drizzle-orm/supabase";
import { foreignKey } from "drizzle-orm/pg-core";

// inside the users table's third argument:
foreignKey({
  columns: [table.authUserId],
  foreignColumns: [authUsers.id],
  name: "users_auth_user_id_fkey",
}).onDelete("cascade"), // keep whatever ON DELETE action the generated code had
```

Keep the FK `name` identical to the generated one so the diff stays empty.

- [ ] **Step 4: Handle the view**

If `pull` captured `books_with_essay_count`, move its `pgView` definition into `db/schema/views.ts` verbatim. If it did NOT capture it (Step 4 of Task 2 showed 0), define it as an existing view so Drizzle tracks but never recreates it:

### Task 4: Extract current-state functions and triggers into db/sql/

**Files:**
- Create: `db/sql/functions.sql`
- Create: `db/sql/triggers.sql`

These files are **reference + editing surface**, not applied automatically. They answer "what do our functions/triggers look like right now?" — the cleanup of 30 migrations' worth of fix-on-fix history.

- [ ] **Step 1: Extract function definitions from the local DB**

```bash
docker exec supabase_db_Tappka psql -U postgres -d postgres -tA -c "
SELECT pg_get_functiondef(p.oid) || ';' || E'\n'
FROM pg_proc p
JOIN pg_namespace n ON n.oid = p.pronamespace
LEFT JOIN pg_depend d ON d.objid = p.oid AND d.deptype = 'e'
WHERE n.nspname = 'public'
  AND d.objid IS NULL  -- excludes extension-owned functions (pg_trgm, btree_gist)
ORDER BY p.proname;
" > db/sql/functions.sql
```

Verify: `grep -c "CREATE OR REPLACE FUNCTION" db/sql/functions.sql` returns 20 (the app functions listed in the inventory), and the file contains NO `gbt_` or `gtrgm_` functions.

- [ ] **Step 2: Extract trigger definitions (public tables AND auth.users)**

```bash
docker exec supabase_db_Tappka psql -U postgres -d postgres -tA -c "
SELECT pg_get_triggerdef(t.oid) || ';'
FROM pg_trigger t
JOIN pg_class c ON c.oid = t.tgrelid
JOIN pg_namespace n ON n.oid = c.relnamespace
WHERE NOT t.tgisinternal
  AND n.nspname IN ('public', 'auth')
ORDER BY n.nspname, c.relname, t.tgname;
" > db/sql/triggers.sql
```

Verify: `grep -c "CREATE TRIGGER" db/sql/triggers.sql` returns 20 (16 public + 4 on auth.users).

- [ ] **Step 3: Add a header comment to both files**

Prepend to `db/sql/functions.sql` (and the equivalent to `triggers.sql`):

```sql
-- Current-state reference for all app-owned Postgres functions.
-- NOT applied automatically. To change a function:
--   1. Edit it here.
--   2. pnpm db:generate:custom  (creates an empty migration)
--   3. Paste the changed CREATE OR REPLACE FUNCTION into that migration.
-- Extracted from the live schema on 2026-06-12.
```

```markdown
## Database schema changes

The schema source of truth is `db/schema/*.ts` (Drizzle). Do NOT hand-write
migrations for tables/columns/enums/indexes/RLS policies.

- **Tables, columns, enums, indexes, RLS policies, views:** edit `db/schema/*.ts`,
  then `pnpm db:generate`. Review the generated SQL in `supabase/migrations/`
  (watch for unintended DROPs), then `pnpm supabase migration up`.
- **Functions & triggers:** Drizzle can't model these. Edit the current-state
  file in `db/sql/`, run `pnpm db:generate:custom` to create an empty migration,
  and paste the `CREATE OR REPLACE` statement in.
- Never edit existing files in `supabase/migrations/` and never run schema
  commands against production. Deployment applies migrations the same way as
  before this change.
- App data access stays on `supabase-js`; never add a runtime Drizzle client
  (it would bypass RLS).
```
